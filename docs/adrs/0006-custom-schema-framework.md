# A Custom Framework for Defining Linked Metadata Models

Date: 2024-01-11

## Summary

In the context of **modeling linked metadata on research data**

facing **the performance and development-effort constraints we ran into with the
LinkML-based tooling in our prototype**

we decided for **implementing a custom specification and framework for modelling linked
data based on JSON schema**

and neglected **implementing custom tooling for LinkML or using the schema_salad
package**

to achieve **high performance, ease of development, and flexibility**

accepting that **the custom spec and framework need to be implemented and maintained**.

## Details

### Status

**proposed**

### Context & Requirements

For modeling metadata, we need to be able to not only describe the structure of
individual metadata resources (such as metadata on Files) but also how resources link to
each other (e.g. a dataset resource links to multiple file resources). Since a resource
could be referenced by multiple other resources, the links have to be established by
referencing the ID of the linked resource instead of simply embedding referenced
resources which would result in redundancy.

Moreover, our metadata life cycle concept relies on a submission-centric source of truth that is translated into multiple
read-specific artifacts through an ETL process. Thereby, not only the metadata but
also the underlying model needs to be transformed.

We currently use the LinkML specification for modeling metadata. A first prototype of
an application, called metldata, realizing the metadata life cycle concept based on
tooling around LinkML, was achieved
[here](https://github.com/ghga-de/metldata/tree/d7ad4b1e97de983d3931125366981443ba5c4b81).

This LinkML-based approach came with the following issues:

In our prototype, validation of metadata against a LinkML-based model and manipulation of
LinkML models as part of the transformation workflow was resource-intensive. Executing a
representative transformation workflow on a representative metadata submission took 30 minutes
or more. Our investigation attributed this to schema-validator generation and repeated retrieval
of basic type definitions from the Internet. For the repetitive transformations required by this
workflow, the evaluated tooling did not meet our performance requirements.

Using the LinkML tooling to manipulate models also came with a high development
overhead for us. This was partially due to the design of the metamodel classes of the
linkml_runtime library, which requires many manual checks and type casts because the
annotations for most fields of the dataclasses are ambiguous. It was also due to the
LinkML specification allowing resource properties to be specified in several different
ways (local per-class slot_usage, slot_usage inherited from a class or a mixin, globally
defined slot_usage, locally defined properties), which made the programmatic
manipulations we needed laborious.

We did not find tooling to validate metadata directly against a LinkML schema. Instead,
the schema is on-the-fly translated into a JSON schema representation. The validation is
then performed against the autogenerated JSON schema. Thus the validation capability
of LinkML is reduced to that of JSON schema. Therefore, advanced validation needs
corresponding to the linking of data, such as referencing resources by ID, are not
covered.

In addition to the performance and tooling limitations observed in our prototype, we ran
into several bugs in the version of the LinkML tooling we evaluated, in areas covering
only basic language features. This added implementation risk for our use case. The LinkML
specification also provides a broad set of language features, while the tooling ecosystem
available to us was maintained by a comparatively small community, which made long-term
support a consideration for our project at the time.

To conclude, the initial LinkML-based implementation of metldata came with a level of
complexity and performance overhead that made it unsuitable for upcoming development such
as the transformation of the code base to a microservice architecture or the ability to
process metadata of different models.

### Decision

We decided to use JSON schema directly for modeling the content of resources. In
addition to that, a
lightweight specification and associated framework are implemented to describe and
validate links
between resources. A proof-of-concept for such a specification/framework, called
schemapack, was implemented
[here](https://github.com/ghga-de/schemapack/tree/1f30214d29249888651363f2ea8f3344e90abfe2).
A re-implementation of two transformation steps in the metldata framework was
demonstrated
[here](https://github.com/ghga-de/metldata/tree/1de4873b5c7f6c608ceb38d154bbc6eb5cb7c259).

### Consequences

The schemapack specification provides a clear mental model that separates the concern
of describing the content of resources from the need to model links between resources.

For validating the content of resources, JSON Schema provides an industry-standard
specification with mature tooling backed by a large community making the ecosystem
very reliable. JSON schema is widely known and thus simplifies onboarding team members.

The requirements of modeling links between resources are very basic. Thus the
schemapack specification is very compact, making it easy to understand and maintain.

The framework comes with built-in tooling for isolating individual resources and their
dependencies from a larger data document. Isolated resources can be subsequently integrated
i.e. transformed into an embedded JSON structure that e.g. matches the format expected
to be returned from REST APIs. This makes schemapack instrumental for the use in our
metadata transformation workflows.

As demonstrated in the proof-of-concept implementation in metldata, realizing
transformations using schemapack comes with a small implementation overhead.

Moreover, the runtime for executing transformations of data and metadata is reduced to
the millisecond range. Thus, a full re-implementation of a complex transformation workflow
applied to a typical metadata submission is likely to be complete within a few seconds.
Moreover, the current design allows for further optimization through caching or the
use of alternative libraries for JSON parsing and JSON Schema validation.

The custom specification allows to flexibly introduce additional features related to
linking between resources as needed. E.g. checking the uniqueness of fields other than
the
identifier across resources, or referencing ontologies. The design already comes with a
plugin mechanism that allows adding validation functionality without needing changes to
the core specification or framework.

The main disadvantage of schemapack compared to the current approach is that it requires
the implementation and maintenance of the framework and specification. As already
mentioned, however, this is manageable due to the low complexity required on top of
JSON Schema.

### Alternatives

We have evaluated two alternatives: the use of a package called
[schema_salad](https://github.com/common-workflow-language/schema_salad) and the option
to implement custom tooling for a subset of the LinkML specification.

The schema_salad framework follows a concept similar to LinkML since it combines the
description of resource structures with information on links between resources. It
supports all the features that we currently require including linking by ID. At the time
of evaluation, however, its ecosystem was considerably smaller than that of the JSON
Schema tooling considered here, which we expected to mean less readily available support
for our use case and a larger onboarding effort for our developers. As far as we were
aware, its main adoption at that point was for the Common Workflow Language, so we would
have needed to evaluate its fit for our rather different requirements much more
extensively before adopting it.

The implementation of custom tooling based on a minimal subset of the LinkML language
would come with a much larger overhead than the proposed solution. This is because, for
LinkML, we would not only have to implement features for validating linking between
resources but also capabilities for validating the content of resources. This would
effectively mean replicating the functionality of a JSON Schema validation library or
re-implementing a LinkML to JSON Schema transpiler and subsequently using a
JSON Schema library. Both options come with high complexity. Furthermore, the
benefits from the circumstance that we would not change the specification of the
metadata model are only very limited. Only the metadata model itself might stay without
requiring a major overhaul. However, all implementation work would have to be redone
anyway since the tooling changes. Moreover, the aspects of the LinkML specification that
do not fit our workflow would remain. In our experience it required a considerable
onboarding effort for new engineers, and it combines structural validation and resource
linkage in a single mental model, whereas we wanted to keep these two concerns
separate. We would need to agree on a convention on top of LinkML for structuring
resources of submissions so that they fit the expectations of metldata. Overall making
this option very costly.

### Addendum

The specification and framework described here have since been implemented and released
as a standalone package, `schemapack`. The migration of metldata to it is prepared on a
dedicated branch and has not been merged yet, which is why this ADR is still marked as
proposed.
