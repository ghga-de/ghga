Reading the spacetree

What this draws, and what it leaves out

Nodes are consumers, edges are events

A node is a service reacting; the pill on the edge into it is the event that woke it. The node's left stripe repeats that edge's colour, so a branch's publish mechanism is readable at any zoom.

The root node is the service that publishes first, in the accent colour. Its own box carries no pill because nothing published to reach it — a person or a CLI did.

The DLQ edge is universal

Every node here can also fail. On an unhandled exception hexkit publishes the event to dlq with its type unchanged, and the DLQ service stores it. Drawing that from each node would double every tree, so it is its own entrypoint: DLQS · process next event.

The retry topic is retry-<service_name> (hexkit/providers/akafka/provider/eventsub.py:498).

Excluded: actions with no event

Omitted on purpose: every GET and /health; datasteward-kit metadata submit|transform (file-system event store only); files upload (S3 only); ghga-connector decrypt; DCS /objects/{id}/envelopes; the auth-service claim and grant routes; IVA create-code and delete-iva; and every work-package route.

Also gone: files ingest-upload-metadata, now a dead command.

Excluded: the state management service

SMS exposes POST /events/, which can publish any payload to any topic. It is a test fixture — its own README says it must never be deployed to production — so it is not an entrypoint here.

One quirk in the type names

metldata's artifacts topic uses upserted / deleted — hexkit's hardcoded outbox type names — but it is published with a plain KafkaEventPublisher and consumed with EventSubscriberProtocol. It is drawn as plain, because that is what it is.

Where a branch ends

A dashed node publishes an event that nothing currently subscribes to: studies, audit-records, downloads, file-deletions, staged-files. They are really published — the consumers live outside the repo, or do not exist yet.
