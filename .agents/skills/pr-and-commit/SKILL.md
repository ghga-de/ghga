# Branches, pull requests and commits

The grammar is in the [names section of the conventions](../../../docs/conventions.md#names-branches-prs-commits) and the lengths in the [writing style](../../../docs/style.md#length).
Read the names section first; this skill gives only the order of the steps and the traps.
Do the stage the dev names after the command, or the one the request describes, and stop at its end.

## Branch

1. Take the kind from the conventions' table; only a `hotfix` is cut from `main`.
2. Ask for the YouTrack key if the dev has not given one, and go on without it if there is none.
3. In a stack, the key goes in front of the stack name when the issue covers the whole stack, and in front of the description when it covers only this PR.
4. Run `git fetch origin` and cut the branch from `origin/dev`, or `origin/main` for a hotfix, never from a local `dev`: it lags behind after every merge.
   In a stack, cut it from the branch below instead.
5. When the main clone holds other work, `just wt <branch>` gives the branch its own worktree, cut from `origin/dev` (pass `origin/main` as the second argument for a hotfix); otherwise `git switch -c <branch> origin/dev`.

## Commit

1. Stage the files of this change by name: `git add -A`, `git add .` and `git commit -a` take whatever else is in the tree.
2. Write the message in the commit form of the grammar without the `(#<PR>)`, which does not exist yet.
   The squash replaces the branch commits, but the reviewer reads them until then.
3. Let the hooks run; when one fails, fix the cause and commit again.
   A commit on `dev` or `main` is refused by `no-commit-to-branch`: branch first.

## Open

1. The title is prose: a capital letter, no `type:` or other label before it, no full stop, the key in parentheses at the end.
   The `pr-title` workflow warns on anything else.
2. Write the description for the reviewer: what changed, why, and what to look at first.
   Not a list of the files, and not a report on how the session went.
3. At most three short paragraphs, about 150 words, each on one line: GitHub shows every newline in a description.
   A description that will not shorten belongs to a PR that should be a stack; propose the split.
4. Keep the checklist of `.github/pull_request_template.md`, and tick a box only for what this session ran and saw pass.
   Name what was not run instead of claiming it.
5. Credit the agent by how much of the change it drafted, not the description: "Generated by Claude Code" for most of it, "Co-authored by Claude Code" for a substantial part, and no line for less.
6. Show the dev the branch, its commits (`git log --oneline origin/dev..HEAD`), the title and the description, then stop.
   Push and run `gh pr create` only after the dev's go for this PR, as a draft if the dev says so.
7. In a stack, each PR's base is the branch below it (`--base`); where the `gh stack` extension is installed, `gh stack init --base dev <branches, bottom first>` and `gh stack submit --auto` link the open PRs.

## Merge

The dev merges; agents may not run `gh pr merge`.
Draft the squash commit for the dev:

1. Read the PR: `gh pr view <n> --json number,title,headRefName,headRefOid,baseRefName,body,files`.
2. The type follows the branch's kind; a `hotfix` is `fix`.
3. The scope is the stack's name in a stack; solo, the member's directory name where one member owns every changed file (`hexkit`, `ghga-connector`), and none otherwise.
4. Write the subject from the title, not as a copy of it: imperative, lower case, no stack and no YouTrack key, ending in `(#<n>)`.
   Count it with the suffix: 52 characters where it fits, 72 at most.
5. Cut the description to three to five bullets, wrapped at 72.
   A breaking change gets `!` after the scope and a `BREAKING CHANGE:` footer.
6. Give the message in a text block ready to paste.

A stack merges PR by PR from the bottom, each with its own message, never with GitHub's button for the whole stack, which keeps the prefills.
After each squash, the next branch still holds the merged branch's original commits, and a file both changed conflicts.
Run `git fetch origin` and give the dev `git rebase --onto origin/dev <old head of the merged PR> <next branch>` and `git push --force-with-lease` to run; agents may not force-push.
The old head is the merged PR's `headRefOid`.

## Cleanup

1. Run `git fetch --prune`; `git branch -vv` marks a branch whose remote was deleted `[gone]`, and `git worktree list` shows the worktrees.
2. Treat a gone branch as merged only when its PR merged (`gh pr list --state merged --head <branch>`, or the dev says so); a remote branch can also be deleted unmerged, so ask about the others.
3. For each worktree of a merged branch, show `git -C <path> status --short`.
   Remove a clean one with `just wt-rm <name>`, or `git worktree remove <path>` outside `.claude/worktrees/`, after `git worktree unlock <path>` if it is locked.
   Ask the dev about one with changes, and never pass `--force`, which discards them.
4. Delete the branch with `git branch -D`: after a squash, `-d` refuses it as unmerged.
5. Leave `dev`, `main` and the branch the main clone has checked out.

## Review replies

1. Collect the open threads: `gh pr view <n> --comments` and `gh api repos/ghga-de/ghga/pulls/<n>/comments`.
2. For each, the dev decides: fix, answer or disagree; you draft.
3. Lead with the decision, then the reason: "Fixed: …" or "Kept as is: … because …".
   No thanks, no praise, no recap of the comment.
4. Post only when asked (`gh pr comment` and `gh pr review` ask first), and never resolve a thread: that is the reviewer's.

## Traps

- GitHub prefills the squash subject with the PR title, which is prose and carries the key: it is never the commit subject as it stands.
- No `Co-authored-by:` trailer for an agent in a commit, even when the dev asks for one: say that the conventions rule it out, and offer the credit line in the description.
- A title with a Conventional Commits prefix (`fix: …`) is not a commit subject waiting to be reused; rewrite both.
- After a squash merge, `git log origin/dev..<branch>` still lists the branch's commits, though their content is in `dev`: it never shows whether a branch merged.
- A go to open one PR is not a go to push the next, nor to push again after a change.
